# Wire Protocol — Runtime Bridge (HTTP + SSE)

Normative, language-neutral specification for the Runtime Bridge feature.
Both host runtimes (Rust server on wasmtime, JS client on the jco-transpiled
composite) MUST conform to this document and to the canonical shapes in
`contracts/shared/wire_protocol.golden.json`. One concept, one definition:
do not re-define a shape already covered by the golden file or by a WIT
vocabulary record.

Decision register: see `DECISIONS_RUNTIME_BRIDGE.md`.

## 1. Concepts

- **Core side** — the side where the singleton WASM runner lives (client or
  server). Session state stays here.
- **Peer** — the opposite side.
- **Control channel** — an SSE stream from server to client
  (`GET /antikythera/v1/events`). The server pushes tool-execution requests,
  hook requests, LLM tokens, forwarded runner events, and lifecycle signals
  on this channel. The client never initiates over SSE; it responds via
  POST-back.
- **POST-back** — the client answers a server-initiated request by POSTing to
  `POST /antikythera/v1/events/{correlation-id}/response`.
- **Correlation id** — an opaque string generated by the sender. It MUST
  round-trip on the POST-back. A response whose correlation id is not known
  (expired or unknown) is ignored and logged. Timeouts and retries are
  defined per request family in §5.
- **Union registry** — the merged set of tool definitions from the client
  side, the server side, and MCP servers. Each tool has exactly one owner in
  `{server, client, mcp}`. The loop owner computes the union and pushes it to
  the runner in a single `register-tools` call (the runner replaces the whole
  registry on every call).
- **Destination** — the routing target for a tool call:
  `local` (the core side executes it), `remote` (the peer executes it),
  `mcp` (a third-party MCP server executes it; always server-side).
- **Gate** — a permission check. Every denial MUST be surfaced as an error
  whose message starts with `permission:`. There is no silent degradation.

## 2. Endpoints

All paths are versioned under `/antikythera/v1`. Content type is
`application/json` except the SSE stream.

| Method | Path | Purpose | Request body | Response body |
|---|---|---|---|---|
| POST | `/antikythera/v1/llm/call` | Proxy an LLM call (all LLM traffic goes through the server) | `llm-request` shape | `llm-response` shape |
| POST | `/antikythera/v1/tools/execute` | Execute a `server`- or `mcp`-owned tool | `tool-call-event` shape | `tool-execution-result` shape |
| GET | `/antikythera/v1/tools` | Registry pull (discovery, C1) | — | array of `ToolDefinition` |
| GET | `/antikythera/v1/events` | SSE control channel; query `client_id` REQUIRED, `session_id` optional | — | SSE stream |
| POST | `/antikythera/v1/events/{correlation-id}/response` | POST-back for server-initiated requests | `{correlation_id, ok, payload, error?}` | empty 204 |
| POST | `/antikythera/v1/state/{context-id}` | Reserved "future" (decision d, D2) — NOT exposed by this delivery | — | — |
| GET | `/antikythera/v1/state/{context-id}` | Reserved "future" (decision d, D2) — NOT exposed by this delivery | — | — |

### 2.1 `POST /antikythera/v1/llm/call`

Streaming is signaled by the QUERY PARAMETER `?stream=true` on this endpoint
(one concept, one definition — it is NOT signaled inside the JSON body). When
`stream=true`, the response body carries the final `llm-response` shape as
usual, and the server additionally pushes each token as an `llm-token` event
on the control channel (see §4).

Body is the `llm-request` vocabulary record shape (WIT `vocabulary.llm-request`):

```json
{
  "provider": "ollama",
  "model": "gpt-oss:120b-cloud",
  "session_id": "session-123",
  "messages_json": "[{\"role\":\"user\",\"content\":\"hi\"}]",
  "force_json": false,
  "temperature": 0.7,
  "max_tokens": 512,
  "schema_name": null,
  "metadata_json": null
}
```

Response is the `llm-response` vocabulary record shape. Streaming is NOT done
on this endpoint: LLM tokens travel as `llm-token` events on the control
channel when the caller requests streaming (see §4).

### 2.2 `POST /antikythera/v1/tools/execute`

Body is the `tool-call-event` vocabulary record shape; the server executes a
`server`- or `mcp`-owned tool and returns a `tool-execution-result` shape:

```json
{
  "tool-name": "get_current_time",
  "arguments-json": "{}",
  "session-id": "session-123",
  "step-id": 1
}
```

```json
{
  "tool-name": "get_current_time",
  "success": true,
  "output-json": "{\"datetime\":\"2026-08-12T00:00:00Z\"}",
  "error-message": null,
  "step-id": 1
}
```

A gate denial MUST return HTTP 403 with body `{"error": "permission: ..."}`.

### 2.3 `GET /antikythera/v1/tools`

Returns the peer-side tool definitions as an array of `ToolDefinition`
objects (`{name, title?, description, parameters?, input_schema?,
output_schema?}`). Used by the loop owner for pull-on-demand discovery (C1).

### 2.4 `GET /antikythera/v1/events`

SSE stream. Query parameters: `client_id` (REQUIRED, opaque), `session_id`
(optional — the lifecycle scope, per-session vs per-client, is developer
policy, decision 8). The stream sends `: keepalive` comments and
`id:` fields for resume/reconnect.

Event envelope:

```json
{
  "type": "tool-execution-request",
  "correlation_id": "corr-0001",
  "session_id": "session-123",
  "client_id": "client-a",
  "payload": {}
}
```

Event `type` ∈ `{tool-execution-request, hook-request, llm-token,
event-forward, registry-sync, lifecycle, error}`.

### 2.5 `POST /antikythera/v1/events/{correlation-id}/response`

POST-back body:

```json
{
  "correlation_id": "corr-0001",
  "ok": true,
  "payload": {},
  "error": null
}
```

On gate denial `ok` is `false` and `error` MUST start with `permission:`.

## 3. Message families

### 3.1 `tool-execution-request` (SSE, server → client)

Server asks the client to execute a `client`-owned tool. Payload is the
`tool-call-event` shape. The client responds via POST-back with
`tool-execution-result` as `payload`.

### 3.2 `hook-request` (SSE, server → client)

Server asks the client to provide a runtime-hook decision. Payload:

```json
{
  "hook": "decide-action",
  "session_state_json": "{}",
  "input_json": "{}"
}
```

`hook` ∈ `{prepare-turn, decide-action, handle-tool-result}`. The client
responds via POST-back; `payload` is the hook decision string exactly as the
`runtime-hooks` WIT function would return it (a JSON object string, or
`{"passthrough": true}`).

### 3.3 `llm-token` (SSE, server → client)

```json
{
  "session_id": "session-123",
  "chunk": "Hello",
  "correlation_id": null
}
```

The client feeds each chunk to `append-llm-chunk`.

### 3.4 `event-forward` (SSE, server → client)

Server forwards runner events (e.g. `tool_requested`, `tool_result`,
`session_archived`) drained from the runner when the core runs on the server,
so the client UI can render progress. Payload is the raw runner event.

### 3.5 `registry-sync` (SSE, server → client)

Optional push notification that the peer registry changed. Payload is an
array of `ToolDefinition`. The loop owner MAY re-pull via `GET /tools`
instead (C1 default).

### 3.6 `lifecycle` (SSE, server → client)

Signals: `connected`, `ready`, `error`, `heartbeat`. `error` payload MUST
carry the `permission:`-style message when the error is a gate denial.

### 3.7 `error` (SSE, server → client)

Transport-level error envelope. Gate denials use the `permission:` prefix.

## 4. LLM streaming flow

1. Client (core on client) or server (core on server) calls
   `prepare-user-turn` and builds the message list.
2. The core side calls `POST /antikythera/v1/llm/call?stream=true` (always
   the server proxy) with streaming requested.
3. The server proxies to the configured provider (including local-dev
   Ollama) and pushes each token as an `llm-token` event on the control
   channel.
4. The client feeds tokens to `append-llm-chunk` and calls
   `commit-llm-stream` on completion.

## 5. Timeouts and retries

- Correlation ids expire after a server-defined TTL (default 60s). A POST-back
  whose correlation id is unknown is ignored and logged.
- A `tool-execution-request` or `hook-request` without a POST-back within TTL
  surfaces as an explicit error on the core side (`permission:`-style
  fail-closed, no silent hang): the caller receives an error envelope.
- SSE reconnect uses the last `id:` field for resume; the client re-registers
  its `client_id` on reconnect.

## 6. Mapping to the runner contract

- Wire `tool-execution-result` → runner `ToolResultInput`:
  `{tool_name, success, output_json, error_message?, correlation_id?}`.
  `step_id` is dropped (the runner derives it from session state);
  `output_json` is REQUIRED (the runner rejects the non-`_json` field);
  `correlation_id` is forwarded from the pending call when present.
- Wire hook decisions → `runtime-hooks` WIT functions verbatim
  (`(string, string) -> result<string, string>`).
- The core side calls `process-tool-result-for-session` with the mapped
  `ToolResultInput` after any tool execution, local or remote.
